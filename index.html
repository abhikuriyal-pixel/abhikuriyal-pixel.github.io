Development

DocFoo project

Explore DocFoo / GitHub

DocFoo is a fast, vectorless, non-agentic retrieval engine for technical papers, books and documents. I built it to keep answers confined to the sources you actually work with. It retrieves the evidence first, then lets a local or cloud model write the answer, with citations and original figures, tables and code. The core is written in Rust, and a small local model can handle the answer-writing step.

Integration with PiKins

The easiest way to work with DocFoo. Import and index your documents in PiKins, then chat with DocFoo like a teammate. Open cited passages in the reader, ask questions beside the text, or continue the same conversation on Telegram.

Integration with Hermes

Already using Hermes? Set up the DocFoo plugin once, then start your document questions with dfq in Slack or another connected chat. DocFoo looks through your library and returns answers with citations and original figures. Hermes delivers the answer without rewriting it.

Integration with coding agents

The same DocFoo skill works with Pi, OpenCode, Codex and Claude Code. It tells the agent when to scan, index and query your documents, and how to keep source citations and original figures in the answer.

PiKins

Explore PiKins / GitHub

PiKins is a collaborative desktop app for working with persistent AI teammates. Each teammate has its own model, memory and workspace. Talk to them directly, or ask Chief to delegate work and bring their reports together. I built it for knowledge workers who need reliable document answers through DocFoo, alongside reactive marimo notebooks, connected apps and a browser. You choose the tools each teammate can use and review actions that need your approval.

Model ports for llama.cpp

I’m implementing less-common architectures in llama.cpp, a lightweight C/C++ inference engine for running language and vision-language models locally. For CPU/GPU edge deployments, its wider choice of low-bit quantization formats, fast native kernels and lean runtime can make it a better fit than ONNX Runtime, particularly when memory and runtime overhead matter. The goal is simple: useful models running locally, without a heavy inference stack.

FalconOCR

I’m bringing FalconOCR, TII’s 270M-parameter OCR model, to llama.cpp. It processes image patches and text in a single Transformer. With about 30% of GLM-OCR’s 900M parameters and comparable OCR performance in the model authors’ reported evaluations, it is a promising fit for memory-constrained edge devices.
